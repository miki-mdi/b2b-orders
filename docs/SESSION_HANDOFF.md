## 2. Auth / RLS architecture (as it stands today)

- **Identity**: single global `User` table + `TenantMembership` (seller-side) + `CustomerMembership` (buyer-side), not separate Seller/Customer user tables - see [DATABASE_DESIGN.md](DATABASE_DESIGN.md) §4.
- **Auth.js v5**, Credentials provider, JWT sessions (Credentials forces JWT - DB sessions aren't possible with it). The `jwt` callback re-resolves the active membership from the database on every request via `resolveActiveMembership()`, so a deactivated user/membership/suspended tenant loses access on the next request, not just at token expiry.
- **Three-layer tenant/customer isolation**:
  1. **Layer 2 (app)**: a Prisma Client Extension (`src/lib/db/scoped-client.ts`) auto-injects `tenantId`/`customerId` into every query against a scoped model, driven by AsyncLocalStorage context set by `withTenantContext`/`withCustomerContext` (`src/lib/db/with-tenant.ts`).
  2. **Layer 3 (RLS)**: PostgreSQL Row-Level Security on every tenant-owned table, keyed on `app.current_tenant_id` (required) and `app.current_customer_id` (optional, narrows buyer-facing tables to one customer). Source of truth: [prisma/rls/policies.sql](../prisma/rls/policies.sql).
  3. **A third, narrowly-scoped exemption**: `app.current_user_id`, used ONLY by `withUserContext()` (`src/lib/db/with-user-context.ts`) for the login/membership-discovery step, where no tenant is known yet. It's a **SELECT-only** RLS exemption on exactly two tables (`TenantMembership`, `CustomerMembership`) letting a user read their own membership rows across tenants; INSERT/UPDATE/DELETE policies on both tables are unchanged and still require a real tenant context - identity alone can never create or modify a membership.
- **Domain services never accept tenantId/customerId from the browser** - every seller route calls `requireSellerSession()` (`src/lib/auth/require-seller.ts`) server-side to get the tenantId from the session, never from a route param or form field. Phase 1C added the symmetric buyer-side guard, `requireBuyerSession()` (`src/lib/auth/require-buyer.ts`). **Phase 1D added no new guard** - every seller-order screen and Server Action reuses `requireSellerSession()` unchanged, including the seller-entered-order flow (the seller's own tenantId, never a customerId or tenantId read from form input, is what scopes every write).
- Every catalog/customer/pricing mutation writes an `AuditLogEntry` in the same transaction as the change (`src/lib/domain/audit/audit-log.ts`). Phase 1C followed the same rule for order creation and buyer-initiated cancellation. **Phase 1D extends the helper itself** (see §1) so a field-level entry (`fieldName: "confirmedQty"`, `fieldName: "status"`) can be written alongside the existing whole-row style, and uses it for every seller confirmation, line adjustment, and status transition (see §12).
- **No arbitrary status from the browser**: each of the four forward-transition buttons (Picking/Ready/Out for delivery/Delivered) is its own Server Action with the target status hardcoded server-side (`src/app/[locale]/seller/orders/[id]/actions.ts`) - a request can never smuggle in an arbitrary `OrderStatus` string, since there is no code path that reads one from form data.

## 3. Known issues discovered and fixed (all resolved, all covered by regression tests unless noted)

1. **RLS `::uuid` cast bug** (fixed in migration 2): policies cast the session variable to `uuid` and compared against columns that are actually `TEXT` (Prisma's client-generated ids, not native `uuid`). Fixed to plain text comparison throughout.
2. **Connection-reuse RLS bug** (fixed in migration 2): once a pooled connection had `app.current_customer_id` set at least once, a later transaction on that same connection that never set it again saw `current_setting(...)` return `''` (empty string), not `NULL` - silently restricting a seller-only session as if it were scoped to a nonexistent customer. Fixed with `NULLIF(..., '') IS NULL` everywhere that check appears. Regression test: `tests/isolation/connection-reuse.test.ts`.
3. **Structural login bug** (fixed in migration 4): `resolveActiveMembership()` could never see a real membership row, because RLS on `TenantMembership`/`CustomerMembership` required a tenant context that doesn't exist yet during login - discovering the tenant *is* the point of that query. Fixed with the `app.current_user_id` exemption described in §2. Regression tests: `tests/auth/membership-discovery.test.ts`.
4. **Stale uncontrolled-input UI bug** (Phase 1B, code fix only, no migration): the customer's price-list-assignment `<select>` and discount `<input>` use `defaultValue` (uncontrolled), which doesn't re-sync when a Server Action updates the data without a redirect. Fixed by keying `PricingSection` on the current values so it remounts on an actual change (`src/app/[locale]/seller/customers/[id]/edit/page.tsx`). Found and verified via manual browser testing, not automated tests (it's a client-rendering issue, not a data-correctness one).
5. **Order-number allocation race** (Phase 1C, code fix only, no migration - found and fixed during implementation, before the commit): `submitOrder`'s order-number aggregate originally ran inside the buyer's `withCustomerContext` transaction. RLS's Tier 2 customer-narrowing (by design - see [SECURITY_AND_MULTI_TENANCY.md](SECURITY_AND_MULTI_TENANCY.md) §2) meant that query only ever saw the *current customer's own* orders, not the whole tenant's - so two different customers submitting their first order both computed "next number = 1" and collided on the `(tenantId, orderNumber)` unique constraint. This surfaced immediately in `tests/buyer/order-history-isolation.test.ts`. Fixed by reading the tenant-wide max via a separate `withTenantContext` call (no row content exposed, just a count) before opening the customer-scoped write transaction; `submitOrder` retries up to 5 times on a unique-constraint conflict. See `src/lib/domain/orders/order-service.ts`'s `attemptSubmitOrder` for the exact reasoning left in comments there. This fix already covers Phase 1D's seller-entered orders too, since they call the same `submitOrder`.
6. **Next.js 16 `middleware.ts` → `proxy.ts` rename** (Phase 1C, found during manual browser verification, not caught by any automated test): Next.js 16 deprecated the `middleware.ts` file convention in favor of `proxy.ts` (must also live under `src/`, alongside `src/app`, not at the repo root). This project's `middleware.ts` was written against the old convention and was **silently never invoked** - which meant next-intl's locale redirect/rewrite never ran for any bare, unprefixed URL. Fixed by replacing `middleware.ts` with `src/proxy.ts` (same `createMiddleware(routing)` call, just the file convention Next.js 16 now expects). Verified by hand in the browser pane. Not covered by an automated test (no existing test suite exercises the Next.js routing/middleware layer directly).
7. **Buyer order detail never showed who placed the order** (Phase 1D, code fix only, no migration): a display gap left over from Phase 1C, not a Phase 1D regression - `Order.placedByName`/`placedByRole` were always captured correctly, but the buyer-facing order detail page never rendered them. This only became worth fixing once a seller could place an order on a buyer's behalf (Phase 1D) and the buyer would otherwise have no way to tell. Fixed in `src/app/[locale]/buyer/orders/[id]/page.tsx`: the "Placed by" line now shows whenever `placedByRole` isn't one of the buyer's own roles (`BUYER_ADMIN`/`BUYER_EMPLOYEE`). Verified live in the browser pane (see §7).

None of these are open. Note on process, not code: an earlier draft of the Phase 1D commit message incorrectly attributed item 5 (order-number race) to Phase 1D's own work; that was caught and corrected before the commit was finalized - the fix and its regression test both actually date to Phase 1C, unchanged since.

## 4. Pricing resolution rules

`resolveEffectivePrice(tenantId, customerId, productUnitId)` in `src/lib/domain/pricing/pricing-resolution.ts` - written in Phase 1B specifically for "the future Buyer flow to reuse as-is." Phase 1C's buyer catalog/cart and **Phase 1D's seller-entered-order flow** all call it unchanged, with no buyer-specific or seller-specific fork of the pricing logic anywhere. Checked in this exact order, failing safe (a typed `reason`, never a guess or a throw) at every step:

1. Customer must be active (`CUSTOMER_INACTIVE` otherwise).
2. The `Product` **and** its `ProductUnit` must both be active - checked *before* visibility, so an inactive item is unavailable regardless of any override (`PRODUCT_INACTIVE` / `PRODUCT_UNIT_INACTIVE`).
3. Visibility: visible by default; an explicit `CustomerProductVisibility` row of `HIDDEN` overrides that (`HIDDEN_FOR_CUSTOMER`). A `VISIBLE` row is a no-op (visible is already the default).
4. Customer must have an active `CustomerPriceListAssignment`, pointing at an active `PriceList` (`NO_ASSIGNMENT` otherwise, including when the assigned list has been deactivated).
5. That price list must have a `PriceListItem` for this exact `productUnitId` - no fallback to another packaging or another list (`NO_PRICE` otherwise).
6. The customer's flat `discountPercent` (0-100, no promotions engine) is applied **after** the base price-list price: `finalPrice = basePrice * (1 - discountPercent / 100)`, rounded to 2 decimals. No discount on file behaves as 0%.

The buyer catalog silently excludes any `ProductUnit` this function reports unavailable for, rather than showing it as disabled/greyed-out. **A seller entering an order gets no bypass of any of this** - see §13.

## 8. Cart architecture (Phase 1C, unchanged by Phase 1D)

**Decision: browser-persisted (localStorage), not server/session-persisted.** See `src/lib/cart/cart-storage.ts`'s header comment for the full reasoning; summary:

- The cart holds **only** `{ productUnitId, quantity }` pairs - never a price, name, or anything else that could go stale or be trusted. This is what makes "browser-persisted" safe: there is nothing sensitive or authoritative to protect in browser storage.
- No new table, no migration, no RLS policy - a server-persisted cart would have needed its own tenant/customer-scoped table and RLS surface for state that has zero historical or audit value once an order is actually placed.
- Implemented as a small external store (`src/lib/cart/cart-store.ts`) read via React's `useSyncExternalStore` (not `useState` + `useEffect`) - this project's lint config (`react-hooks/set-state-in-effect`) flags synchronous `setState` calls inside effects, and `useSyncExternalStore`'s server/client snapshot split is also the *correct* fix for the hydration-mismatch problem a naive "read localStorage on mount" effect would otherwise have.
- Scoped per-browser, not per-account: a buyer working across two devices simply has two independent carts. Acceptable for MVP; a cross-device cart would be a Phase 2+ upgrade to a real server-persisted design, not a small tweak to this one.

**Phase 1D's seller-entered-order basket is a deliberately separate, simpler thing** (`src/app/[locale]/seller/orders/new/seller-basket-context.tsx`): plain in-memory React Context state, not localStorage. A seller only ever fills it out in one linear page visit (pick customer → add items → submit), so there is no cross-page-navigation persistence need the buyer cart has; reusing the buyer's localStorage cart would also have risked mixing a seller's in-progress basket with whatever the same browser's *own* buyer cart holds, if the same person is ever signed in as both. Same safety property either way: only `{ productUnitId, quantity }` is held, never a price.

**Server-side re-pricing/revalidation rule (never trust the browser):** every place a cart or basket's contents are turned into something priced or orderable goes through the exact same function, `resolveCartLine` (`src/lib/domain/orders/cart-resolution.ts`), which re-fetches from the database and ignores anything the caller might otherwise believe about price or availability - used by the buyer's cart/checkout preview, the seller-entered-order basket preview, and (a third and final, authoritative time) `submitOrder` itself, for both flows. If any line fails re-resolution at submission time, the **entire order is rejected** with a structured `LINE_ISSUES` result naming which `productUnitId`s failed and why - never a partial order nobody asked for.

## 9. Order submission / snapshot rules (Phase 1C, extended by Phase 1D)

`submitOrder` (`src/lib/domain/orders/order-service.ts`) is the only path that creates an `Order` - **used by both the buyer's own checkout and Phase 1D's seller-entered-order flow**, distinguished only by an `actingContext` parameter (`"CUSTOMER"` vs `"TENANT"`) added in Phase 1D. Per line, in order:

1. Every line is resolved via `resolveCartLine` (§8) *before* any database write begins - if any line is invalid, nothing is written at all.
2. The customer must still be active and the delivery address must still belong to that customer and be active, both re-checked inside the write transaction.
3. The order number is allocated from a **tenant-wide** read (see §3 item 5), with retry-on-conflict.
4. The soft cut-off warning (`cutOffWarningShown`) is computed server-side from the tenant's `cutOffTime` and the requested delivery date.
5. Per [DATABASE_DESIGN.md](DATABASE_DESIGN.md) §6, `productNameSnapshot`/`productSkuSnapshot`/`unitLabelSnapshot`/`unitPriceAtOrderTime` (base price)/`discountPercentAtOrderTime`/`vatRateAtOrderTime`/`requestedQty` are snapshotted onto each `OrderLine` and never re-derived from live catalog data again. `confirmedQty`/`deliveredQty` stay `null` until Phase 1D's confirmation step.
6. `Order.deliveryAddressSnapshot` (JSON) captures the full address at submission time.
7. The order is created directly in `SUBMITTED` status with `submittedAt` set.
8. One `AuditLogEntry` (`action: "CREATE"`, `entityType: "Order"`, `actingContext` as passed in) is written in the same transaction as the order - **Phase 1D's seller-entered path additionally sets `reason: "Entered by seller on behalf of customer"` on this entry** when `actingContext` is `"TENANT"`, so the audit trail alone (independent of `placedByRole`) tells the two paths apart.
9. Totals are never stored as columns - computed on demand by `src/lib/domain/orders/order-totals.ts`. **Phase 1D added two more computations to that same file**: `computeSubmittedOrderTotals` (always from `requestedQty`, ignoring any confirmation) and `computeLineFulfillment` (`requestedQty`/`confirmedQty`/derived `unavailableQty` per line) - see §11.

## 10. Order status state machine (Phase 1D)

`src/lib/domain/orders/order-status-machine.ts` is the **single source of truth** for which status transitions are legal - every seller-side status change and the buyer's own cancellation call `isValidOrderTransition`/`assertValidOrderTransition` from this one module, rather than checking status rules inline in a Server Action.

```
SUBMITTED → CONFIRMED → PICKING → READY → OUT_FOR_DELIVERY → DELIVERED
SUBMITTED → CANCELLED   (buyer-only, see requestOrderCancellation in order-service.ts)
```

`DELIVERED` and `CANCELLED` are fully terminal (no outgoing transition at all). `DRAFT` has no modeled outgoing transition either, since nothing in this codebase creates a `DRAFT` order yet. **Deliberately out of scope for Phase 1D**, per `docs/ORDER_WORKFLOW.md` §3 ("handled manually by the Seller Admin, not a guided flow") and the Phase 1D brief's own scoping: seller-initiated cancellation from `CONFIRMED` or later. If that's wanted later, it is a small, additive change to `ORDER_STATUS_TRANSITIONS` plus a new Server Action - not a rearchitecture.

Every transition, including the four forward-only ones (`confirmOrder`'s implicit `SUBMITTED → CONFIRMED`, and `advanceOrderStatus` for `PICKING`/`READY`/`OUT_FOR_DELIVERY`/`DELIVERED`), writes an `AuditLogEntry` with `fieldName: "status"`, the old and new status, and the acting seller's user id, in the same transaction as the status change.

## 11. Confirmation, partial fulfillment, and totals rules (Phase 1D)

`confirmOrder` (`src/lib/domain/orders/order-fulfillment-service.ts`) is the only path that moves an order `SUBMITTED → CONFIRMED`. Locked rules, all enforced server-side against the database's own `requestedQty` (never the form's):

- A seller may **reduce** `confirmedQty` below `requestedQty` (partial fulfillment) or set it to **0** (the line becomes unavailable; `unavailableReason` is set to the same reason).
- A seller must **never increase** `confirmedQty` above `requestedQty` - rejected as `EXCEEDS_REQUESTED_QTY` with nothing written, per the Phase 1D brief ("without an explicit future business rule").
- Any actual change (`confirmedQty !== requestedQty`) **requires a reason**, checked in the domain function itself (not only the zod schema) - rejected as `REASON_REQUIRED` otherwise. A negative quantity is also rejected at the domain layer as defense in depth, even though the schema already excludes it.
- If the whole submission is invalid (any line's issue, or a line the seller's UI didn't account for), **nothing is written** - confirmation is all-or-nothing, exactly like `submitOrder`.
- `requestedQty` and every price/discount/VAT snapshot field are **never** touched by confirmation - only `confirmedQty` (and conditionally `unavailableReason`) on `OrderLine`, and `status`/`confirmedAt` on `Order`.

**Partial fulfillment is represented per line, never as a separate top-level order status** - `docs/ORDER_WORKFLOW.md` §1 item 1 rejected a `PARTIALLY_CONFIRMED` status for exactly this reason, and Phase 1D followed that decision rather than revisiting it. `computeLineFulfillment` (`order-totals.ts`) derives `unavailableQty = requestedQty - confirmedQty` on demand - it is never its own stored column.

**Totals, the one rule to remember**: `computeSubmittedOrderTotals(lines)` always reflects the order **exactly as the buyer/seller originally submitted it** (computed from `requestedQty`, ignoring `confirmedQty` entirely) - this is the permanent historical record and is always reconstructable even after confirmation, because nothing about the original submission was ever mutated. `computeOrderTotals(lines)` (the same function Phase 1C already had) reflects the **current** state, preferring `confirmedQty` once it's set. The order detail page shows both, side by side, once any line has been confirmed - verified live in the browser (§7): submitted totals stayed at 590.00 while confirmed totals correctly showed 354.00 after a partial confirmation.

## 12. Seller-entered order design and attribution (Phase 1D)

A seller creates an order for a customer from `/seller/orders/new` (`src/app/[locale]/seller/orders/new/`): pick a customer (from the seller's own tenant, via `listCustomers`) → browse that customer's own catalog (`listBuyerCatalog`, reused unchanged) → add items to an in-memory basket (§8) → pick one of that customer's own active addresses → submit.

**No duplicated business logic**: the submission calls the exact same `submitOrder`/`resolveCartLine` the buyer's own checkout uses (§9), just with `actingContext: "TENANT"` instead of `"CUSTOMER"`. Concretely, this means, verified by test and live in the browser:
- The customer's own discount/price-list/visibility rules apply unchanged - a product hidden for that customer is still hidden from the seller creating an order for them.
- The seller cannot manually set or override a price - the stored `unitPriceAtOrderTime` always matches whatever the database resolves at submission time, exactly like the buyer path.
- Min-order-quantity/increment rules apply unchanged.
- A customer id, delivery address, or product unit from a different tenant is rejected the same way the buyer path would reject it (via the same tenant/customer-scoped queries - there is no seller-specific relaxation of any check).

**Attribution** - "record that the order was entered by seller on behalf of customer," satisfied two ways with no new schema:
1. `Order.placedByUserId`/`placedByName`/`placedByRole` record the *seller* (e.g. "Alpha Seller Admin", `"SELLER_ADMIN"`) as who placed it - these fields already existed and already mean "who placed this order," distinct from `customerId` ("whose order it is").
2. The `CREATE` `AuditLogEntry` for the order carries `actingContext: "TENANT"` and `reason: "Entered by seller on behalf of customer"` - independently recoverable from the audit trail even without looking at `placedByRole`.

The buyer still sees the order normally in their own order history/detail (customer isolation is unaffected by who created it), and - since Phase 1D also fixed the display gap in §3 item 7 - now sees the "Placed by Alpha Seller Admin (SELLER_ADMIN)" line on their own order detail page too, so there's no ambiguity about how the order got there.

## 13. Notification / order-event approach (Phase 1D)

`src/lib/domain/orders/order-events.ts` is a small in-process listener registry, published to (`publishOrderEvent`) **after** the write transaction that produced the event has already committed - never from inside a `withTenantContext`/`withCustomerContext` callback, so a future real listener failing can never roll back an order change. One event type per meaningful transition: `SUBMITTED`, `CONFIRMED`, `PICKING`, `READY`, `OUT_FOR_DELIVERY`, `DELIVERED`, `CANCELLED`. The only listener registered today logs a structured line; a listener failing is caught and logged, never thrown, so it can't break the operation it's describing.

**Deliberately not a `Notification` database table**: per the Phase 1D brief's explicit instruction not to integrate any external channel yet, and because a `Notification` row would need its own tenant/customer scoping and RLS policy for something nothing in this phase reads back. The actual operationally-meaningful record of "what happened and why" is already `AuditLogEntry` (§2), which every one of these same call sites already writes in the same transaction as the change. `order-events.ts` exists purely so a future real notification provider (email/SMS/push) has exactly one place to subscribe (`onOrderEvent`), instead of needing to be wired into every order-mutating call site individually.

## 14. Phase 1E: pilot hardening

Phase 1E (commit `df0c1da`) picked up Option A from the previous revision of this file's "Proposed Phase 1E options" section (pilot hardening), plus the dashboard-metrics item from Option B. Scope: prepare the app for a real pilot with 1-3 seller tenants by improving operational visibility, auditability, exports, diagnostics, and production-readiness - **no new business modules, no schema change**.

**Auth documentation reconciliation, done first per the brief.** [SECURITY_AND_MULTI_TENANCY.md](SECURITY_AND_MULTI_TENANCY.md) §5 and [ARCHITECTURE.md](ARCHITECTURE.md) previously still described the original "database-backed sessions" design, even though `src/lib/auth/auth.ts` had documented the actual JWT-with-per-request-re-resolution implementation since Phase 0 (Auth.js's Credentials provider hard-requires JWT sessions - there is no supported way around it). The docs were corrected to match the working implementation; **no auth code changed**.

**Audit log UI** (`src/lib/domain/audit/audit-query-service.ts`, `/seller/audit`): a read-only, tenant-scoped, paginated view of `AuditLogEntry`, filterable by date range, actor, entity type, and action. Entity references (which order/customer/product an entry is about) are resolved to a human-readable label via a handful of batched queries per page - not one query per row - and only within the same tenant-scoped transaction, so a resolved reference can never leak another tenant's row. The append-only write path (`audit-log.ts`) is untouched; nothing in the application can edit or delete an entry.

**Order activity timeline** (`src/lib/domain/orders/order-activity-service.ts`, on the seller order detail page): a human-readable history built **entirely from persisted `AuditLogEntry` rows** for that order and its lines - creation, quantity adjustments (with reason), every status transition, cancellation. Deliberately invents nothing: an order created by the seed script's raw Prisma call (not `submitOrder`) correctly shows no creation event, because none was ever written.

**CSV export** (`src/lib/domain/export/export-service.ts` + `/api/seller/export/{customers,products,price-lists,orders,order-lines}`, linked from `/seller/exports`): each export is tenant-scoped, UTF-8 with a BOM (so Excel renders Cyrillic names correctly), capped at 20,000 rows (`EXPORT_ROW_CAP`, with an `X-Export-Truncated` response header if hit), and writes its own `AuditLogEntry` (`entityType: "Export"`) in the same transaction as the read. Orders/order-lines exports include `submittedTotal` and `confirmedTotal` computed the same way the order detail page does. CSV **import** was explicitly out of scope.

**Dashboard metrics** (`src/lib/domain/dashboard/dashboard-service.ts`, `/seller`): order-status pipeline counts (one `groupBy`), active customer/product-unit counts, and the 10 most recent orders - a fixed, small number of queries regardless of tenant size, no background aggregation job.

**Platform diagnostics** (`src/lib/auth/require-platform-admin.ts`, `src/lib/domain/diagnostics/diagnostics-service.ts`, `/admin/diagnostics`): a new Layer 4 guard (`requirePlatformAdminSession`, mirroring `requireSellerSession`/`requireBuyerSession`) restricts this to `isPlatformAdmin` sessions only - verified live that a seller admin and a buyer are both redirected to `/`. Reports app status, environment, app version (read from `package.json`), git commit (from a `GIT_COMMIT_SHA`/`VERCEL_GIT_COMMIT_SHA`/`SOURCE_VERSION` env var, `"unknown"` if unset - never shells out to `git`), database connectivity/latency (`SELECT 1`), migration state (name/count/date from `_prisma_migrations`, which the app's low-privilege role can read via the existing `GRANT ... ON ALL TABLES`), and two boolean-only configuration checks (`DATABASE_URL`/`AUTH_SECRET` configured or not). **Never returns a connection string, secret, token, or raw environment variable** - covered by `tests/admin/diagnostics.test.ts`, which asserts the serialized report never contains the actual `DATABASE_URL`/`AUTH_SECRET` values or a `postgres://` pattern.

**Structured logging and error handling**: `src/lib/logging/logger.ts` is a minimal `{level, message, timestamp, ...metadata}` JSON-line logger - no external vendor, per the brief. `order-events.ts`'s two `console.log`/`console.error` calls (§13) now go through it. A new `route-error-boundary.tsx` component backs `error.tsx` files under `seller/`, `buyer/`, and `admin/`, showing a friendly message plus the Next.js-generated `digest` (never a stack trace or raw error message - Next.js already redacts Server Component error messages in production) with a retry button. **Naming note for this Next.js build specifically**: the error boundary's recovery callback prop is `retry`, not the `reset` name from older Next.js versions - confirmed against `node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md` per this repo's `AGENTS.md` instruction to check the pinned docs before writing new code, since this checkout has Next.js 16-era breaking changes.

**Pagination**: `src/lib/pagination.ts` provides shared `clampPage`/`clampPageSize` (ceiling `MAX_PAGE_SIZE = 100`)/`clampSearchTerm` (ceiling `MAX_SEARCH_TERM_LENGTH = 200`) helpers. New `listOrdersForTenantPage`/`listCustomersPage`/`listProductsPage` domain functions (server-side `skip`/`take` + `count`) back the orders/customers/products list pages and the audit log page. The original unpaginated `listOrdersForTenant`/`listCustomers`/`listProducts` were **left unchanged** for their other callers (tests, the seller-entered-order customer dropdown) rather than changed in place, to avoid touching working, tested code that doesn't need pagination.

**Performance review finding (no migration needed)**: `AuditLogEntry`'s existing indexes - `(tenantId, entityType, entityId)` and `(tenantId, createdAt)` - are adequate for the audit log UI's queries at pilot scale (1-3 tenants). Filtering by `actorUserId` or `action` alone isn't separately indexed; this is a deliberate non-issue for now, not an oversight - if audit volume grows well past pilot scale, `(tenantId, actorUserId)` and `(tenantId, action)` would be the first candidates, added then with a real migration, not preemptively.

**Tests**: 232 passing (up from 205; 27 new - see §5), covering tenant isolation for the audit log and all five export types (including RLS-only bypass tests), the activity timeline's chronological-and-nothing-invented behavior, CSV escaping, pagination clamping, and the diagnostics report's no-secrets guarantee. `npm run lint`, `npm run typecheck`, `npm run build`, and `prisma validate`/`prisma generate` are all clean as of `df0c1da`.
