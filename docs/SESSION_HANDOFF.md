## 2. Auth / RLS architecture (as it stands today)

- **Identity**: single global `User` table + `TenantMembership` (seller-side) + `CustomerMembership` (buyer-side), not separate Seller/Customer user tables - see [DATABASE_DESIGN.md](DATABASE_DESIGN.md) §4.
- **Auth.js v5**, Credentials provider, JWT sessions (Credentials forces JWT - DB sessions aren't possible with it). The `jwt` callback re-resolves the active membership from the database on every request via `resolveActiveMembership()`, so a deactivated user/membership/suspended tenant loses access on the next request, not just at token expiry.
- **Three-layer tenant/customer isolation**:
  1. **Layer 2 (app)**: a Prisma Client Extension (`src/lib/db/scoped-client.ts`) auto-injects `tenantId`/`customerId` into every query against a scoped model, driven by AsyncLocalStorage context set by `withTenantContext`/`withCustomerContext` (`src/lib/db/with-tenant.ts`).
  2. **Layer 3 (RLS)**: PostgreSQL Row-Level Security on every tenant-owned table, keyed on `app.current_tenant_id` (required) and `app.current_customer_id` (optional, narrows buyer-facing tables to one customer). Source of truth: [prisma/rls/policies.sql](../prisma/rls/policies.sql).
  3. **A third, narrowly-scoped exemption**: `app.current_user_id`, used ONLY by `withUserContext()` (`src/lib/db/with-user-context.ts`) for the login/membership-discovery step, where no tenant is known yet. It's a **SELECT-only** RLS exemption on exactly two tables (`TenantMembership`, `CustomerMembership`) letting a user read their own membership rows across tenants; INSERT/UPDATE/DELETE policies on both tables are unchanged and still require a real tenant context - identity alone can never create or modify a membership.
- **Domain services never accept tenantId/customerId from the browser** - every seller route calls `requireSellerSession()` (`src/lib/auth/require-seller.ts`) server-side to get the tenantId from the session, never from a route param or form field. Phase 1C added the symmetric buyer-side guard, `requireBuyerSession()` (`src/lib/auth/require-buyer.ts`). **Phase 1D added no new guard** - every seller-order screen and Server Action reuses `requireSellerSession()` unchanged, including the seller-entered-order flow (the seller's own tenantId, never a customerId or tenantId read from form input, is what scopes every write).
- Every catalog/customer/pricing mutation writes an `AuditLogEntry` in the same transaction as the change (`src/lib/domain/audit/audit-log.ts`). Phase 1C followed the same rule for order creation and buyer-initiated cancellation. **Phase 1D extends the helper itself** (see §1) so a field-level entry (`fieldName: "confirmedQty"`, `fieldName: "status"`) can be written alongside the existing whole-row style, and uses it for every seller confirmation, line adjustment, and status transition (see §12).
- **No arbitrary status from the browser**: each of the four forward-transition buttons (Picking/Ready/Out for delivery/Delivered) is its own Server Action with the target status hardcoded server-side (`src/app/[locale]/seller/orders/[id]/actions.ts`) - a request can never smuggle in an arbitrary `OrderStatus` string, since there is no code path that reads one from form data.

## 3. Known issues discovered and fixed (all resolved, all covered by regression tests unless noted)

1. **RLS `::uuid` cast bug** (fixed in migration 2): policies cast the session variable to `uuid` and compared against columns that are actually `TEXT` (Prisma's client-generated ids, not native `uuid`). Fixed to plain text comparison throughout.
2. **Connection-reuse RLS bug** (fixed in migration 2): once a pooled connection had `app.current_customer_id` set at least once, a later transaction on that same connection that never set it again saw `current_setting(...)` return `''` (empty string), not `NULL` - silently restricting a seller-only session as if it were scoped to a nonexistent customer. Fixed with `NULLIF(..., '') IS NULL` everywhere that check appears. Regression test: `tests/isolation/connection-reuse.test.ts`.
3. **Structural login bug** (fixed in migration 4): `resolveActiveMembership()` could never see a real membership row, because RLS on `TenantMembership`/`CustomerMembership` required a tenant context that doesn't exist yet during login - discovering the tenant *is* the point of that query. Fixed with the `app.current_user_id` exemption described in §2. Regression tests: `tests/auth/membership-discovery.test.ts`.
4. **Stale uncontrolled-input UI bug** (Phase 1B, code fix only, no migration): the customer's price-list-assignment `<select>` and discount `<input>` use `defaultValue` (uncontrolled), which doesn't re-sync when a Server Action updates the data without a redirect. Fixed by keying `PricingSection` on the current values so it remounts on an actual change (`src/app/[locale]/seller/customers/[id]/edit/page.tsx`). Found and verified via manual browser testing, not automated tests (it's a client-rendering issue, not a data-correctness one).
5. **Order-number allocation race** (Phase 1C, code fix only, no migration - found and fixed during implementation, before the commit): `submitOrder`'s order-number aggregate originally ran inside the buyer's `withCustomerContext` transaction. RLS's Tier 2 customer-narrowing (by design - see [SECURITY_AND_MULTI_TENANCY.md](SECURITY_AND_MULTI_TENANCY.md) §2) meant that query only ever saw the *current customer's own* orders, not the whole tenant's - so two different customers submitting their first order both computed "next number = 1" and collided on the `(tenantId, orderNumber)` unique constraint. This surfaced immediately in `tests/buyer/order-history-isolation.test.ts`. Fixed by reading the tenant-wide max via a separate `withTenantContext` call (no row content exposed, just a count) before opening the customer-scoped write transaction; `submitOrder` retries up to 5 times on a unique-constraint conflict. See `src/lib/domain/orders/order-service.ts`'s `attemptSubmitOrder` for the exact reasoning left in comments there. This fix already covers Phase 1D's seller-entered orders too, since they call the same `submitOrder`.
6. **Next.js 16 `middleware.ts` → `proxy.ts` rename** (Phase 1C, found during manual browser verification, not caught by any automated test): Next.js 16 deprecated the `middleware.ts` file convention in favor of `proxy.ts` (must also live under `src/`, alongside `src/app`, not at the repo root). This project's `middleware.ts` was written against the old convention and was **silently never invoked** - which meant next-intl's locale redirect/rewrite never ran for any bare, unprefixed URL. Fixed by replacing `middleware.ts` with `src/proxy.ts` (same `createMiddleware(routing)` call, just the file convention Next.js 16 now expects). Verified by hand in the browser pane. Not covered by an automated test (no existing test suite exercises the Next.js routing/middleware layer directly).
7. **Buyer order detail never showed who placed the order** (Phase 1D, code fix only, no migration): a display gap left over from Phase 1C, not a Phase 1D regression - `Order.placedByName`/`placedByRole` were always captured correctly, but the buyer-facing order detail page never rendered them. This only became worth fixing once a seller could place an order on a buyer's behalf (Phase 1D) and the buyer would otherwise have no way to tell. Fixed in `src/app/[locale]/buyer/orders/[id]/page.tsx`: the "Placed by" line now shows whenever `placedByRole` isn't one of the buyer's own roles (`BUYER_ADMIN`/`BUYER_EMPLOYEE`). Verified live in the browser pane (see §7).

None of these are open. Note on process, not code: an earlier draft of the Phase 1D commit message incorrectly attributed item 5 (order-number race) to Phase 1D's own work; that was caught and corrected before the commit was finalized - the fix and its regression test both actually date to Phase 1C, unchanged since.

## 4. Pricing resolution rules

`resolveEffectivePrice(tenantId, customerId, productUnitId)` in `src/lib/domain/pricing/pricing-resolution.ts` - written in Phase 1B specifically for "the future Buyer flow to reuse as-is." Phase 1C's buyer catalog/cart and **Phase 1D's seller-entered-order flow** all call it unchanged, with no buyer-specific or seller-specific fork of the pricing logic anywhere. Checked in this exact order, failing safe (a typed `reason`, never a guess or a throw) at every step:

1. Customer must be active (`CUSTOMER_INACTIVE` otherwise).
2. The `Product` **and** its `ProductUnit` must both be active - checked *before* visibility, so an inactive item is unavailable regardless of any override (`PRODUCT_INACTIVE` / `PRODUCT_UNIT_INACTIVE`).
3. Visibility: visible by default; an explicit `CustomerProductVisibility` row of `HIDDEN` overrides that (`HIDDEN_FOR_CUSTOMER`). A `VISIBLE` row is a no-op (visible is already the default).
4. Customer must have an active `CustomerPriceListAssignment`, pointing at an active `PriceList` (`NO_ASSIGNMENT` otherwise, including when the assigned list has been deactivated).
5. That price list must have a `PriceListItem` for this exact `productUnitId` - no fallback to another packaging or another list (`NO_PRICE` otherwise).
6. The customer's flat `discountPercent` (0-100, no promotions engine) is applied **after** the base price-list price: `finalPrice = basePrice * (1 - discountPercent / 100)`, rounded to 2 decimals. No discount on file behaves as 0%.

The buyer catalog silently excludes any `ProductUnit` this function reports unavailable for, rather than showing it as disabled/greyed-out. **A seller entering an order gets no bypass of any of this** - see §13.

## 8. Cart architecture (Phase 1C, unchanged by Phase 1D)

**Decision: browser-persisted (localStorage), not server/session-persisted.** See `src/lib/cart/cart-storage.ts`'s header comment for the full reasoning; summary:

- The cart holds **only** `{ productUnitId, quantity }` pairs - never a price, name, or anything else that could go stale or be trusted. This is what makes "browser-persisted" safe: there is nothing sensitive or authoritative to protect in browser storage.
- No new table, no migration, no RLS policy - a server-persisted cart would have needed its own tenant/customer-scoped table and RLS surface for state that has zero historical or audit value once an order is actually placed.
- Implemented as a small external store (`src/lib/cart/cart-store.ts`) read via React's `useSyncExternalStore` (not `useState` + `useEffect`) - this project's lint config (`react-hooks/set-state-in-effect`) flags synchronous `setState` calls inside effects, and `useSyncExternalStore`'s server/client snapshot split is also the *correct* fix for the hydration-mismatch problem a naive "read localStorage on mount" effect would otherwise have.
- Scoped per-browser, not per-account: a buyer working across two devices simply has two independent carts. Acceptable for MVP; a cross-device cart would be a Phase 2+ upgrade to a real server-persisted design, not a small tweak to this one.

**Phase 1D's seller-entered-order basket is a deliberately separate, simpler thing** (`src/app/[locale]/seller/orders/new/seller-basket-context.tsx`): plain in-memory React Context state, not localStorage. A seller only ever fills it out in one linear page visit (pick customer → add items → submit), so there is no cross-page-navigation persistence need the buyer cart has; reusing the buyer's localStorage cart would also have risked mixing a seller's in-progress basket with whatever the same browser's *own* buyer cart holds, if the same person is ever signed in as both. Same safety property either way: only `{ productUnitId, quantity }` is held, never a price.

**Server-side re-pricing/revalidation rule (never trust the browser):** every place a cart or basket's contents are turned into something priced or orderable goes through the exact same function, `resolveCartLine` (`src/lib/domain/orders/cart-resolution.ts`), which re-fetches from the database and ignores anything the caller might otherwise believe about price or availability - used by the buyer's cart/checkout preview, the seller-entered-order basket preview, and (a third and final, authoritative time) `submitOrder` itself, for both flows. If any line fails re-resolution at submission time, the **entire order is rejected** with a structured `LINE_ISSUES` result naming which `productUnitId`s failed and why - never a partial order nobody asked for.

## 9. Order submission / snapshot rules (Phase 1C, extended by Phase 1D)

`submitOrder` (`src/lib/domain/orders/order-service.ts`) is the only path that creates an `Order` - **used by both the buyer's own checkout and Phase 1D's seller-entered-order flow**, distinguished only by an `actingContext` parameter (`"CUSTOMER"` vs `"TENANT"`) added in Phase 1D. Per line, in order:

1. Every line is resolved via `resolveCartLine` (§8) *before* any database write begins - if any line is invalid, nothing is written at all.
2. The customer must still be active and the delivery address must still belong to that customer and be active, both re-checked inside the write transaction.
3. The order number is allocated from a **tenant-wide** read (see §3 item 5), with retry-on-conflict.
4. The soft cut-off warning (`cutOffWarningShown`) is computed server-side from the tenant's `cutOffTime` and the requested delivery date.
5. Per [DATABASE_DESIGN.md](DATABASE_DESIGN.md) §6, `productNameSnapshot`/`productSkuSnapshot`/`unitLabelSnapshot`/`unitPriceAtOrderTime` (base price)/`discountPercentAtOrderTime`/`vatRateAtOrderTime`/`requestedQty` are snapshotted onto each `OrderLine` and never re-derived from live catalog data again. `confirmedQty`/`deliveredQty` stay `null` until Phase 1D's confirmation step.
6. `Order.deliveryAddressSnapshot` (JSON) captures the full address at submission time.
7. The order is created directly in `SUBMITTED` status with `submittedAt` set.
8. One `AuditLogEntry` (`action: "CREATE"`, `entityType: "Order"`, `actingContext` as passed in) is written in the same transaction as the order - **Phase 1D's seller-entered path additionally sets `reason: "Entered by seller on behalf of customer"` on this entry** when `actingContext` is `"TENANT"`, so the audit trail alone (independent of `placedByRole`) tells the two paths apart.
9. Totals are never stored as columns - computed on demand by `src/lib/domain/orders/order-totals.ts`. **Phase 1D added two more computations to that same file**: `computeSubmittedOrderTotals` (always from `requestedQty`, ignoring any confirmation) and `computeLineFulfillment` (`requestedQty`/`confirmedQty`/derived `unavailableQty` per line) - see §11.

## 10. Order status state machine (Phase 1D)

`src/lib/domain/orders/order-status-machine.ts` is the **single source of truth** for which status transitions are legal - every seller-side status change and the buyer's own cancellation call `isValidOrderTransition`/`assertValidOrderTransition` from this one module, rather than checking status rules inline in a Server Action.

```
SUBMITTED → CONFIRMED → PICKING → READY → OUT_FOR_DELIVERY → DELIVERED
SUBMITTED → CANCELLED   (buyer-only, see requestOrderCancellation in order-service.ts)
```

`DELIVERED` and `CANCELLED` are fully terminal (no outgoing transition at all). `DRAFT` has no modeled outgoing transition either, since nothing in this codebase creates a `DRAFT` order yet. **Deliberately out of scope for Phase 1D**, per `docs/ORDER_WORKFLOW.md` §3 ("handled manually by the Seller Admin, not a guided flow") and the Phase 1D brief's own scoping: seller-initiated cancellation from `CONFIRMED` or later. If that's wanted later, it is a small, additive change to `ORDER_STATUS_TRANSITIONS` plus a new Server Action - not a rearchitecture.

Every transition, including the four forward-only ones (`confirmOrder`'s implicit `SUBMITTED → CONFIRMED`, and `advanceOrderStatus` for `PICKING`/`READY`/`OUT_FOR_DELIVERY`/`DELIVERED`), writes an `AuditLogEntry` with `fieldName: "status"`, the old and new status, and the acting seller's user id, in the same transaction as the status change.

## 11. Confirmation, partial fulfillment, and totals rules (Phase 1D)

`confirmOrder` (`src/lib/domain/orders/order-fulfillment-service.ts`) is the only path that moves an order `SUBMITTED → CONFIRMED`. Locked rules, all enforced server-side against the database's own `requestedQty` (never the form's):

- A seller may **reduce** `confirmedQty` below `requestedQty` (partial fulfillment) or set it to **0** (the line becomes unavailable; `unavailableReason` is set to the same reason).
- A seller must **never increase** `confirmedQty` above `requestedQty` - rejected as `EXCEEDS_REQUESTED_QTY` with nothing written, per the Phase 1D brief ("without an explicit future business rule").
- Any actual change (`confirmedQty !== requestedQty`) **requires a reason**, checked in the domain function itself (not only the zod schema) - rejected as `REASON_REQUIRED` otherwise. A negative quantity is also rejected at the domain layer as defense in depth, even though the schema already excludes it.
- If the whole submission is invalid (any line's issue, or a line the seller's UI didn't account for), **nothing is written** - confirmation is all-or-nothing, exactly like `submitOrder`.
- `requestedQty` and every price/discount/VAT snapshot field are **never** touched by confirmation - only `confirmedQty` (and conditionally `unavailableReason`) on `OrderLine`, and `status`/`confirmedAt` on `Order`.

**Partial fulfillment is represented per line, never as a separate top-level order status** - `docs/ORDER_WORKFLOW.md` §1 item 1 rejected a `PARTIALLY_CONFIRMED` status for exactly this reason, and Phase 1D followed that decision rather than revisiting it. `computeLineFulfillment` (`order-totals.ts`) derives `unavailableQty = requestedQty - confirmedQty` on demand - it is never its own stored column.

**Totals, the one rule to remember**: `computeSubmittedOrderTotals(lines)` always reflects the order **exactly as the buyer/seller originally submitted it** (computed from `requestedQty`, ignoring `confirmedQty` entirely) - this is the permanent historical record and is always reconstructable even after confirmation, because nothing about the original submission was ever mutated. `computeOrderTotals(lines)` (the same function Phase 1C already had) reflects the **current** state, preferring `confirmedQty` once it's set. The order detail page shows both, side by side, once any line has been confirmed - verified live in the browser (§7): submitted totals stayed at 590.00 while confirmed totals correctly showed 354.00 after a partial confirmation.

## 12. Seller-entered order design and attribution (Phase 1D)

A seller creates an order for a customer from `/seller/orders/new` (`src/app/[locale]/seller/orders/new/`): pick a customer (from the seller's own tenant, via `listCustomers`) → browse that customer's own catalog (`listBuyerCatalog`, reused unchanged) → add items to an in-memory basket (§8) → pick one of that customer's own active addresses → submit.

**No duplicated business logic**: the submission calls the exact same `submitOrder`/`resolveCartLine` the buyer's own checkout uses (§9), just with `actingContext: "TENANT"` instead of `"CUSTOMER"`. Concretely, this means, verified by test and live in the browser:
- The customer's own discount/price-list/visibility rules apply unchanged - a product hidden for that customer is still hidden from the seller creating an order for them.
- The seller cannot manually set or override a price - the stored `unitPriceAtOrderTime` always matches whatever the database resolves at submission time, exactly like the buyer path.
- Min-order-quantity/increment rules apply unchanged.
- A customer id, delivery address, or product unit from a different tenant is rejected the same way the buyer path would reject it (via the same tenant/customer-scoped queries - there is no seller-specific relaxation of any check).

**Attribution** - "record that the order was entered by seller on behalf of customer," satisfied two ways with no new schema:
1. `Order.placedByUserId`/`placedByName`/`placedByRole` record the *seller* (e.g. "Alpha Seller Admin", `"SELLER_ADMIN"`) as who placed it - these fields already existed and already mean "who placed this order," distinct from `customerId` ("whose order it is").
2. The `CREATE` `AuditLogEntry` for the order carries `actingContext: "TENANT"` and `reason: "Entered by seller on behalf of customer"` - independently recoverable from the audit trail even without looking at `placedByRole`.

The buyer still sees the order normally in their own order history/detail (customer isolation is unaffected by who created it), and - since Phase 1D also fixed the display gap in §3 item 7 - now sees the "Placed by Alpha Seller Admin (SELLER_ADMIN)" line on their own order detail page too, so there's no ambiguity about how the order got there.

## 13. Notification / order-event approach (Phase 1D)

`src/lib/domain/orders/order-events.ts` is a small in-process listener registry, published to (`publishOrderEvent`) **after** the write transaction that produced the event has already committed - never from inside a `withTenantContext`/`withCustomerContext` callback, so a future real listener failing can never roll back an order change. One event type per meaningful transition: `SUBMITTED`, `CONFIRMED`, `PICKING`, `READY`, `OUT_FOR_DELIVERY`, `DELIVERED`, `CANCELLED`. The only listener registered today logs a structured line; a listener failing is caught and logged, never thrown, so it can't break the operation it's describing.

**Deliberately not a `Notification` database table**: per the Phase 1D brief's explicit instruction not to integrate any external channel yet, and because a `Notification` row would need its own tenant/customer scoping and RLS policy for something nothing in this phase reads back. The actual operationally-meaningful record of "what happened and why" is already `AuditLogEntry` (§2), which every one of these same call sites already writes in the same transaction as the change. `order-events.ts` exists purely so a future real notification provider (email/SMS/push) has exactly one place to subscribe (`onOrderEvent`), instead of needing to be wired into every order-mutating call site individually.

## 15. Phase 1F-A: CSV import, validation/preview, auditability, onboarding readiness

Phase 1F-A (commit `05bfc8a`) picked up the CSV-import item Phase 1E deferred (§14's "CSV import was explicitly out of scope"). Scope: let a seller tenant safely onboard/update Categories, Units of Measure, Products, ProductUnits, Customers, CustomerAddresses, PriceLists, and PriceListItems from a CSV file, without weakening tenant isolation, pricing rules, the audit model, or data integrity. **Order import stayed explicitly out of scope.**

**Stable business keys (`Category.code`, `CustomerAddress`'s `(customerId, label)`) - the one schema change.** Every importable entity needs a translation-independent identifier to match a CSV row against ("never use translated display names as the primary import identity" - the brief's own instruction). `UnitOfMeasure.code`, `Product.sku`, `ProductUnit.sku`, `PriceList.code`, `Customer.code` already had one. Two didn't:
- `Category` had only `nameMk`/`nameEn`. Fixed by adding `code String?` with `@@unique([tenantId, code])` - nullable and optional in the manual form, mirroring `Customer.code`/`PriceList.code` exactly. Pre-existing categories simply have no code until a seller sets one (manually - the field was also added to the Category create/edit form - or via an import CREATE).
- `CustomerAddress` had `label` (free text, e.g. "Main warehouse") with no uniqueness constraint. Fixed by adding `@@unique([customerId, label])` - **no new column**, just formalizing what `label` already meant in practice. A preflight query for existing duplicate `(customerId, label)` pairs found zero before this was applied (a duplicate would have broken the constraint).

Both are in migration `20260920100000_add_import_stable_keys` (§1). Neither needed an RLS policy change - policies are per-table, not per-column (confirmed against `prisma/rls/policies.sql`).

**Workflow (never writes during preview).** Upload → parse/validate/plan (read-only) → preview table (totals, per-row CREATE/UPDATE/NO_CHANGE/ERROR, errors/warnings) → explicit confirm → execute → result summary + downloadable result CSV. The wizard (`src/app/[locale]/seller/imports/[type]/import-wizard.tsx`) is a client component holding the selected `File` in React state; both the preview and confirm Server Actions (`actions.ts`) re-parse and re-plan the **same file** from scratch server-side - the server never trusts a client-echoed plan. Nothing is persisted between steps; the result CSV is generated in memory and handed straight to the browser as a download.

**Architecture** (`src/lib/domain/import/`): a dependency-free RFC4180-ish `csv-parser.ts` (mirrors `export/csv.ts`'s "one place for CSV rules" philosophy - BOM stripping, quoted/escaped fields, embedded newlines, malformed-row detection that never throws) feeds a shared `driver.ts` (`planAndExecuteRows`: normalize → in-file duplicate-key rejection → resolve references → diff against the DB → classify → execute-if-confirming), which every `<entity>-import.ts` plugs into via six functions (`normalizeRow`/`keyOf`/`resolve`/`diff`/`executeCreate`/`executeUpdate`). `import-service.ts` (`previewImport`/`confirmImport`) ties parsing, the driver, and the audit write together per import type.

**Reuse, not duplication.** Each of the 8 relevant domain services (`category-service.ts`, `unit-of-measure-service.ts`, `product-service.ts`, `product-unit-service.ts`, `customer-service.ts`, `customer-address-service.ts`, `customer-discount-service.ts`, `price-list-service.ts`, `price-list-item-service.ts`) gained a tx-scoped `...InTx` core (e.g. `createCategoryInTx`) extracted from its existing `withTenantContext`-wrapped public function, which now just calls the `...InTx` version. **Public signatures and behavior are unchanged** - verified by re-running all 232 pre-existing tests unmodified. Import's `executeCreate`/`executeUpdate` call these same `...InTx` functions, so a CSV-created row gets the exact same validation and the exact same per-row `AuditLogEntry` a manually-created row gets (§7 of SECURITY_AND_MULTI_TENANCY.md), with `reason` extended to name the import batch.

**Transaction strategy: one atomic transaction per confirmed import, no batching.** The whole confirmed import runs inside a single `withTenantContext` transaction - matching `submitOrder`/`confirmOrder`'s existing all-or-nothing pattern (§9/§11). A row already planned as `ERROR` (validation failure, duplicate key, unresolved reference) is simply skipped, never attempted - that's a normal "rejected" outcome, not a failure. An *unexpected* failure while writing an otherwise-valid `CREATE`/`UPDATE` row (e.g. a genuine unique-constraint race between preview and confirm) rolls back the **entire** transaction - nothing partially written - proven in `tests/import/execution.test.ts` via a fault-injecting `EntityImportOps` wrapping the real category-import ops. This was chosen over per-batch transactions deliberately: at the pilot-scale row cap (5,000/import), a single Postgres transaction with a few thousand writes is well within normal bounds, and batching would add real partial-success/resume complexity for no measured benefit - see the performance numbers below.

**Reference resolution is per-row, not batched - verified acceptable at pilot scale.** Each row's `resolve()` issues its own targeted `findFirst` query per reference column (e.g. ProductUnit import does 3: product-by-sku, unit-by-code, existing-row-by-sku), not one batched `findMany` across the whole file. This is a genuine, known characteristic of the current implementation, not an oversight papered over - it was measured directly (see performance sanity below) and found fine at the 5,000-row cap. If real tenant volumes ever grow well past pilot scale, batching the reference lookups (one `findMany({ where: { code: { in: [...] } } })` per referenced entity type per import, instead of per row) would be the concrete next optimization - not something to build speculatively now.

**Tenant isolation & security.** Every reference (`categoryCode`, `productSku`, `unitOfMeasureCode`, `customerCode`, `priceListCode`, `productUnitSku`) resolves through the tenant-scoped `tx` (Layer 2 + RLS, same double enforcement as everywhere else in the app) - a code that only exists in another tenant simply doesn't resolve, proven in `tests/import/tenant-isolation.test.ts` including a case where two tenants reuse the identical business code without colliding. A `tenantId`/`id` column in an uploaded file is ignored, never trusted (tested). Limits: 5 MB max file size, 5,000 max data rows, 2,000 max chars/cell, all checked before parsing.

**CSV formula-injection hardening**, requested for both the new import result CSV and (per the brief's §14 review requirement) retrofitted into every existing export: `sanitizeForSpreadsheet` (new, in `export/csv.ts`) prefixes a cell starting with `= + - @` or tab/CR with a leading `'`, applied inside the shared `escapeCell` used by every `toCsv` call. This was a real, previously-unaddressed gap in the Phase 1E exports (§14 of that phase never mentioned it) - a customer/product name starting with one of those characters would have exported as a live formula. Covered by `tests/import/security.test.ts` (unit-level) and `tests/seller/export-security.test.ts` (end-to-end through a real `exportCustomersCsv` call).

**Audit & result reporting.** One summary `AuditLogEntry` per confirmed import (`entityType: "Import"`, `entityId: "<importType>:<batchId>"`, `action: "CREATE"`, `newValue: {batchId, fileName, created, updated, unchanged, rejected}`), plus the normal per-row entries described above, all tagged `Imported via CSV batch <batchId>` in their `reason`. The existing Audit Log page's entity-type filter picked up "Import" automatically - no code change needed there. The downloadable result CSV (`row, result, key, entityId, message`) is generated in memory and never persisted server-side at any stage.

**Performance sanity (1,000-row local fixtures, `tests/import/performance-sanity.test.ts`).** Customers: preview ≈0.8s, confirm ≈3.2s. ProductUnits (2 FK lookups/row via `resolve()`): preview ≈1.5s, confirm ≈4.6s. An all-`NO_CHANGE` re-import of the same 1,000 customers: ≈0.7s. Comfortably within the 5,000-row cap without needing batching (see above).

**8 import types, each with a downloadable template** (`/api/seller/import/template/<type>`, `src/lib/domain/import/templates.ts`): `categories` (key `code`), `units` (key `code`), `products` (key `sku`, resolves `categoryCode` - **required**, since `createProductInTx` already requires a category for every product), `product-units` (key `sku`, resolves `productSku`+`unitOfMeasureCode`; changing which product a unit belongs to via import is rejected as `CANNOT_REPARENT`, matching the manual UI's own immutability), `customers` (key `code`, plus a `discountPercent` column applied via the same `customer-discount-service.ts` the manual UI uses, with full 3-state absent/blank/set semantics), `customer-addresses` (key `customerCode`+`label`, resolves `customerCode`), `price-lists` (key `code`), `price-list-items` (key `priceListCode`+`productUnitSku`, resolves both).

**Upsert semantics, exact rules**: a column **absent** from the CSV header leaves the existing value untouched on update; a column **present but blank** clears an optional field; required fields can never be blanked via update (empty required cell = row `ERROR`); a business key repeated within the same file rejects **every** row sharing it, first occurrence included - never "last row wins."

## 16. Phase 1F-A follow-up: responsive layout fix (768px horizontal overflow)

Reported after a manual review: at 768px, the Imports wizard's results table (`min-w-[640px]`, wrapped in its own `overflow-x-auto` box) forced the **whole page** wider than the viewport instead of scrolling within its own box - `document.documentElement.scrollWidth` (930) exceeded `clientWidth` (768), confirmed via direct DOM inspection (`getBoundingClientRect()`/`scrollWidth` checks), not just a screenshot.

**Root cause**: `SellerLayout`'s `<main>` (`src/app/[locale]/seller/layout.tsx`) is a flex item along the row's main axis once `md:flex-row` applies (≥768px). Flex items default to `min-width: auto`, which resolves to the item's min-content size unless overridden. Once the sidebar's 224px left `<main>` less than the table's 640px, that min-content size forced the entire row wider than the viewport. Not visible at mobile (`flex-col` below `md:` - width is the cross axis there, unaffected) or desktop (640px comfortably fits) - only in the `md:flex-row` transition zone. No other seller page forces a table `min-width`, so nothing else had exercised this latent issue before.

**Fix** (commit `b437197`): `min-w-0` on `<main>` - the standard override for this flexbox default. Verified: `scrollWidth`/`clientWidth` now match exactly at 375/768/1280px, the table still scrolls inside its own box at 768px (visible internal scrollbar), no regression on the existing Audit Log page's own wide table, and all 317 tests/lint/typecheck/build stayed green.

## 18. Phase 1F-B1: role separation and authorization

Phase 1F-B1 (commit `223c64f`) picked up the first item from Phase 1F-A's own proposed-next-steps list: Sales Rep / Warehouse Worker / Delivery Driver role separation. Scope, approved in three rounds before any code was written (initial matrix proposal → clarifications on Delivery Driver scope, Sales Rep limited edit, and read-only UI → final sign-off): centralize authorization so every seller page, Server Action, and API route enforces a role-appropriate capability server-side, with UI hiding as cosmetic only. **No schema change, no migration, no RLS change** - role trust is layered on top of the existing session at the same trust level `tenantId` already has (see docs/SECURITY_AND_MULTI_TENANCY.md §3's Layer 4).

Gated **before invocation**, not just hidden in the rendered UI: the seller dashboard page (`src/app/[locale]/seller/page.tsx`) only calls the new analytics function at all when the session holds this capability, so a Warehouse Worker or Delivery Driver session never runs either underlying query - including under direct `?range=...` query-string tampering, verified live (§7).

**Fixed MVP business timezone**: `Europe/Skopje` (`src/lib/domain/dashboard/date-range.ts`, `DASHBOARD_TIMEZONE`) - a deliberate, explicit single-region-MVP convention, not derived from the server process's ambient timezone and not a per-tenant setting (that would be a schema change, out of scope). Chosen to match `Tenant`'s own existing `defaultCurrency: "MKD"` / `locale: "mk"` defaults. **Documented here explicitly so a future multi-region phase knows this is the one constant to replace with a per-tenant timezone column** - nothing about the analytics queries themselves (`src/lib/domain/dashboard/sales-analytics-service.ts`) would need to change, only how the boundary instants are computed.

**Date ranges** (`resolveDashboardDateRange`, pure and DB-free, unit-tested in isolation): Today / This week / This month / Custom, every range **inclusive start, exclusive end** (`[from, to)`), computed against Europe/Skopje wall-clock time via the native `Intl.DateTimeFormat` API (no date-library dependency):
- **Today**: midnight-to-midnight in Europe/Skopje. Correctly reflects the real Europe/Skopje DST transitions (a 23-hour day in spring, a 25-hour day in autumn) rather than a naive fixed-24h assumption - proven by scanning every day of March/October 2026 in the test, not by hardcoding which date the transition falls on.
- **This week**: **Monday-start**, per the approved European/ISO-8601 convention - proven for every day of a test week, independent of which weekday `now` itself is.
- **This month**: 1st of the month through the 1st of the next month, correctly rolling over the year at December.
- **Custom**: caller-supplied `from`/`to` calendar dates (`YYYY-MM-DD`, date-only). **`to` is treated as an inclusive calendar day**, implemented internally as the exclusive upper bound of the *next* day's start - avoiding the classic `23:59:59.999` fencepost/timezone bug. Validated server-side: both dates must parse and round-trip (rejects a calendar-impossible date like `2026-02-30`, which `Date.UTC` would otherwise silently normalize into March), `from` must not be after `to`, and the span is capped at **366 days** (`MAX_CUSTOM_RANGE_DAYS`) to bound query cost - matching the same "explicit, tested limit" philosophy as `EXPORT_ROW_CAP`/`MAX_PAGE_SIZE` elsewhere in the app. Any invalid input falls back to Today rather than erroring the page, while the form retains the user's submitted (invalid) values so they can correct them - verified live (§7).

**"Submitted order value" - exact semantics, deliberately not called "sales value"** (renamed during review specifically because it includes every non-cancelled *submitted* order regardless of what happens to it afterward): `computeSubmittedOrderTotals` (`src/lib/domain/orders/order-totals.ts`, unchanged - already Phase 1D's "permanent historical record" function, §11) summed across every order with a non-null `submittedAt` in the selected range **except `CANCELLED`**. Always computed from `requestedQty` and the frozen per-line snapshot fields (`unitPriceAtOrderTime`, `discountPercentAtOrderTime`, `vatRateAtOrderTime`) - **never** `confirmedQty`, and **never** a live catalog or price-list lookup. Proven by test, not just asserted in a comment: a later partial confirmation at a reduced quantity does not change an already-reported period's value, and neither does a price-list edit made after submission (`tests/dashboard/sales-analytics.test.ts`).

**Top products**: ranked by **requested quantity**, summed per `(productSkuSnapshot, unitLabelSnapshot)` - deliberately not confirmed qty (null until confirmation, and retroactively unstable in the same way the value metric above deliberately avoids), not delivered qty (`OrderLine.deliveredQty` exists on the schema but is never written by any code path in this codebase today - unusable), and not sales value (would need per-line VAT/discount rounding inside the aggregate, losing the single-DB-side-query property below). Grouped by the immutable snapshot SKU/unit-label pair, not the live `productUnitId`, so a since-renamed, reparented, or deleted product/unit still reports correctly - historical reporting stays stable regardless of later catalog changes, per the same principle as the value metric.

**Query strategy - no N+1**: two queries, both O(1) regardless of tenant size (bounded by the 366-day custom-range cap): one `order.findMany` with lines included (Prisma resolves this as one joined round trip, matching the existing `export-service.ts` pattern), summed in memory via the pure `computeSubmittedOrderTotals`; one `orderLine.groupBy` DB-side aggregate for the top-products ranking, matching the shape of the existing `order.groupBy({by: ["status"]})` already in `getDashboardMetrics`. `OrderLine` is not in `TENANT_SCOPED_MODELS` (`src/lib/db/tenant-scoped-models.ts`) - its tenant isolation for this new query comes entirely from RLS (Layer 3), the same trust boundary the existing `exportOrderLinesCsv` already relies on unscoped; proven directly by an RLS-only bypass test.

## 20. Import transaction-timeout robustness fix

A pre-existing production robustness gap, found (not introduced) during Phase 1F-B2 closure and fixed in its own separate commit (`28ad1b6`), precisely because it's an unrelated concern from the dashboard work above: `tests/import/performance-sanity.test.ts` (Phase 1F-A, §15 - **left completely unchanged** by this fix, it's the regression proof, not something adjusted to pass) started failing on this session's machine with a real Prisma error, not a flaky one:

```
Transaction API error: A batch query cannot be executed on an expired transaction.
The timeout for this transaction was 5000 ms, however 5004 ms passed since the start of the transaction.
```

**Root cause**: `withTenantContext` (`src/lib/db/with-tenant.ts`) opens one Prisma interactive transaction per call via `prisma.$transaction(...)`, with no options - so every caller, app-wide, got Prisma's client-level default: `maxWait: 2000`, **`timeout: 5000`**. `previewImport`/`confirmImport` (`src/lib/domain/import/import-service.ts`) each wrap the **entire uploaded file** (up to `MAX_IMPORT_ROWS = 5,000` rows - `src/lib/domain/import/security.ts`) in one such transaction, per the deliberate "one atomic transaction per import, no batching" design from Phase 1F-A §15. A confirmed 1,000-row ProductUnit import (the slowest of the 8 import types - 2 FK lookups/row via the per-row `resolve()` pattern §15 already documented as a known, accepted characteristic) measured **~5.1s real elapsed time** on this machine once unblocked - just over the fixed 5s ceiling, and the original Phase 1F-A measurement (~4.6s) had already been within ~400ms of it. **A real user onboarding a supported-size (up to 5,000-row) catalog could hit this exact "transaction expired" failure** - not a bug in the import logic itself, just a default sized for ordinary request-sized transactions applied to a feature deliberately designed to do much more work in one transaction.

**Fix, narrowly scoped** (`src/lib/db/with-tenant.ts`): `withTenantContext` gained an **optional third parameter**, `options: TenantTransactionOptions` (typed structurally off `prisma.$transaction`'s own signature - the same pattern `scoped-client.ts` already uses for `ScopedTransactionClient`, rather than a hand-written type that could drift from the installed Prisma version), forwarded as-is to `prisma.$transaction(fn, options)`. **Every existing two-argument call site across the entire app is unchanged and unaffected** - each keeps Prisma's defaults exactly as before. Only `previewImport` and `confirmImport` now pass an explicit timeout:
- **`previewImport`: `timeout: 20_000`** (20s) - no writes, so cheaper; measured ~1.9s/1,000 rows for the worst-case entity type, projecting to ~9.4s at the 5,000-row cap.
- **`confirmImport`: `timeout: 60_000`** (60s) - same per-row reads plus the actual writes and a per-row audit log entry; measured ~5.1s/1,000 rows (worst case), projecting to ~25-28s at the 5,000-row cap - 60s leaves roughly 2x margin over that projection.

Both constants live in `src/lib/domain/import/security.ts` (`IMPORT_PREVIEW_TRANSACTION_TIMEOUT_MS` / `IMPORT_CONFIRM_TRANSACTION_TIMEOUT_MS`), next to the existing `MAX_IMPORT_ROWS`/`MAX_FILE_SIZE_BYTES` they're derived from, rather than a new module - moving the existing constants elsewhere would have been unnecessary churn for this fix.

**`maxWait` deliberately left at Prisma's default** (2000ms), everywhere, including for imports: the failure above is unambiguously about `timeout` (how long an already-*started* transaction may keep running - the error text itself says "since the start of the transaction"), not `maxWait` (how long the client waits to *acquire* a transaction slot before starting). There is no evidence of connection-acquisition delay for this feature, and none was introduced by this fix.

**No global Prisma configuration change**: `src/lib/db/prisma.ts` (the shared `PrismaClient` instance every part of the app uses) is untouched - its default transaction timeout remains 5000ms for every other transaction in the app, which stays a useful fast-fail safety net against a genuinely stuck query anywhere else. The longer lock/connection-hold duration this fix accepts (up to 60s instead of 5s, only while a confirmed import is running) is contained to exactly this one feature, which already held that same class of risk at the 5s default per Phase 1F-A's own "one atomic transaction, no batching" design (§15) - this fix extends an already-accepted tradeoff's duration, it does not introduce a new one.

**No schema, migration, RLS, or API/exported-signature change.** `previewImport`/`confirmImport`'s public signatures (parameters, return types) are byte-for-byte unchanged.

**Verification**: `tests/import/performance-sanity.test.ts` run **3 times standalone** after the fix, 3/3 passing every run (9/9 total), with real (no longer artificially truncated at 5000ms) measured numbers: `product-units import (2 FK lookups/row): preview=1886ms confirm=5146ms for 1000 rows` - confirming both that the original ~4.6s Phase 1F-A measurement had genuinely crept past 5000ms on this machine (not a fluke) and that the fix comfortably absorbs it. A new, small, DB-backed unit test (`tests/db/with-tenant-transaction-options.test.ts`) proves the mechanism in isolation from the import feature: an explicit short timeout genuinely aborts a deliberately slow transaction, an explicit longer timeout lets a transaction that sleeps past the 5s default (5.3s) succeed, and an ordinary two-argument call behaves exactly as before. Full suite: 448/448 passing, 48/48 files; `npm run lint`/`npm run typecheck`/`npm run build`/`prisma validate`/`prisma generate` all clean, as of `28ad1b6`.

## 21. Phase 1F-B3: Delivery Driver order assignment

Phase 1F-B3 (commit `aaff752`) picked up the last remaining item from Phase 1F-B1's own proposed-next-steps list (§18, formerly repeated in §21): **Delivery Driver per-order assignment**, so a driver sees only orders assigned to them rather than every tenant order in the delivery-status scope. Scope was approved across several review rounds before any code was written (assignment-model choice → composite-FK design check → mutation-authorization gap → final sign-off) - the same "propose, review, approve" discipline every phase since 1F-B1 has followed. **One schema change** (below); **no RLS policy change**; **no new external dependency**.

**Schema: `Order.assignedDriverMembershipId` references `TenantMembership`, not `User`.** Deliberately - `DELIVERY_DRIVER` is a tenant-membership role, and a bare `User` FK would leave "is this user actually an active driver, in this tenant" as a separate check every call site would have to re-derive, since `User` itself carries no tenant or role (it's explicitly not RLS-protected - see `prisma/rls/policies.sql`'s closing comment). Concretely (migration `20260922215641_add_order_driver_assignment`, §1):
- `Order.assignedDriverMembershipId String?` - nullable, no default; "unassigned" is a first-class state every existing order migrated into, not a migration artifact.
- A new `TenantMembership.@@unique([id, tenantId])` - redundant with `id` alone already being unique, added solely so Postgres has a unique target for the composite FK below.
- **Composite, same-tenant-safe FK**: `Order([assignedDriverMembershipId, tenantId]) -> TenantMembership([id, tenantId])`, `onDelete: Restrict`. This is a real, database-enforced guarantee - Postgres rejects any row where the assigned membership's `tenantId` doesn't match the order's own `tenantId`, independent of and in addition to the application-level check, proven directly by `tests/seller/driver-assignment.test.ts`'s raw-SQL bypass test. Composite FKs default to `MATCH SIMPLE`, so a `NULL assignedDriverMembershipId` exempts the row from the check entirely - unassigned orders are unaffected. `onDelete: Restrict` (not `SetNull`) because a composite FK's `SetNull` would null out *both* columns, including `tenantId`, which must never be null; nothing in this codebase deletes a `TenantMembership` today, and if a future phase adds that, reassigning/clearing any orders first is the correct order of operations anyway.
- Composite index `Order(tenantId, assignedDriverMembershipId, status)` - matches the actual access pattern ("this tenant's orders assigned to membership X, filtered to READY/OUT_FOR_DELIVERY/DELIVERED"), not a bare single-column index.
- **Legacy orders migrate as `NULL`/unassigned** - no backfill, none is possible (nothing in the schema recorded "who actually delivered this" retroactively). **Known, accepted operational consequence**: every existing Delivery Driver session loses visibility into every order it could previously see in READY/OUT_FOR_DELIVERY/DELIVERED, immediately upon this migration, until a Seller Admin/Sales Rep assigns them - worth sequencing (assign a backlog, or train/announce) before this phase reaches a real pilot tenant.

**Authorization: new `orders:assign-driver` capability** (`src/lib/auth/permissions.ts`, same `Capability`/`ROLE_CAPABILITIES` mechanism §18 established), granted to `SELLER_ADMIN` and `SALES_REP` only - `WAREHOUSE_WORKER` and `DELIVERY_DRIVER` cannot assign, reassign, or unassign a driver (a driver cannot even assign themselves). Enforced via the existing `requireSellerCapability`/`checkActionCapability` helpers, no new mechanism.

**Assignment rules** (`assignDriverToOrder`, new `src/lib/domain/orders/driver-assignment-service.ts`): allowed in `SUBMITTED`/`CONFIRMED`/`PICKING`/`READY`/`OUT_FOR_DELIVERY`; rejected as `ORDER_TERMINAL` on `DELIVERED`/`CANCELLED` (reassigning a finished order has no operational meaning). A non-null target membership must resolve inside the same transaction as `{ id: targetMembershipId, tenantId, role: "DELIVERY_DRIVER", isActive: true }` - a cross-tenant, inactive, or wrong-role membership is rejected as `DRIVER_NOT_FOUND_OR_INELIGIBLE`, nothing written. Assignment, reassignment, and unassignment (`targetMembershipId: null`) are the same code path and all write one `AuditLogEntry` (`fieldName: "assignedDriverMembershipId"`) in the same transaction as the order update - this slots directly into the existing order activity timeline (`order-activity-service.ts`) with zero changes to that service, since it already renders arbitrary field-level audit entries generically.

**Driver read visibility** (`getOrderForTenant`/`listOrdersForTenant(Page)` in `order-service.ts`, new optional `driverScope: { membershipId }` parameter, additive to Phase 1F-B1's existing `allowedStatuses`/`statusIn`): a Delivery Driver sees an order only when **both** are true - `assignedDriverMembershipId` equals their own active `DELIVERY_DRIVER` membership id, **and** the status is `READY`/`OUT_FOR_DELIVERY`/`DELIVERED`. An unassigned order, or one assigned to a different driver, comes back `null`/excluded exactly like a cross-tenant or out-of-status order - a direct URL guess with a known orderId 404s, never revealing the order exists (verified live, §7). **Assignment before READY is allowed** (a seller can assign a driver the moment an order is submitted, for planning purposes) **but grants no early visibility** - the driver's own status-scope gate still applies independently, so an early-assigned order stays invisible to that driver until it actually reaches READY. `driverScope` is only ever populated for a `DELIVERY_DRIVER` session; every other role's calls are byte-for-byte unaffected.

**Mutation ownership - the security-critical piece, closed before implementation began.** UI/read scoping alone was judged insufficient: a Delivery Driver must not be able to advance `READY → OUT_FOR_DELIVERY` or `OUT_FOR_DELIVERY → DELIVERED` via a crafted/direct Server Action call carrying a known orderId, even though the button itself would never render for an order they can't see. `advanceOrderStatus` (`order-fulfillment-service.ts`) gained an **optional** `options.requireDriverMembershipId` parameter, checked **inside the same transaction** as the order fetch and status write - existence check, then ownership check (`order.assignedDriverMembershipId !== options.requireDriverMembershipId` → new `NOT_ASSIGNED_DRIVER` reason, nothing written), then the existing state-machine check, in that order. Checking inside the transaction (rather than a separate pre-check read) closes a real TOCTOU race: an Admin reassigning the driver between a pre-check and the actual write could otherwise let a stale driver's request through. **Every other role's call sites never pass this option at all**, so Seller Admin's and Warehouse Worker's transition behavior is structurally unaffected - not a runtime "skip this check for admins" branch, but the option simply never being supplied. `advanceStatusAction` (`[id]/actions.ts`) only computes it for `session.role === "DELIVERY_DRIVER"`.

**Membership resolution: `getOwnActiveTenantMembershipId(tenantId, userId)`** (`driver-assignment-service.ts`) is the one function both the read-scoping and the mutation-ownership check are built on. It re-validates `tenantId` + `userId` + `isActive: true` + `role: "DELIVERY_DRIVER"` **itself**, directly against the database, rather than trusting the caller's already-checked `session.role` - a deliberate fail-closed design so the helper is correct on its own even if a future caller uses it in a context where the role check happened differently or not at all. **No changes to `auth.ts`, the JWT/session callbacks, or the `ActiveMembership`/`SellerSession` shape** - this was an explicit, approved decision (Option A over Option B during planning) to keep the session/auth layer, the most sensitive part of this codebase, completely untouched; the membership id is resolved fresh, server-side, from the trusted `(tenantId, userId)` the session already provides, using `TenantMembership`'s existing `@@unique([userId, tenantId])` index.

**Role-scope regression, explicitly verified, not assumed**: Warehouse Worker's existing `orders:read:fulfillment` scope (`CONFIRMED`/`PICKING`/`READY`) is completely unchanged - driver assignment neither narrows nor widens it, proven by a dedicated regression test and confirmed live (§7). Seller Admin's and Sales Rep's unrestricted `orders:read:all` scope is likewise untouched.

**Tests**: 482 passing (up from 448; 34 new - see §5), including the composite FK's database-level enforcement (a raw-SQL write bypassing all application code is still rejected), every assignment/reassignment/unassignment rule, the mutation-ownership invariant (assigned driver succeeds; a different driver's crafted call is rejected; an unassigned order can't be mutated; early assignment doesn't bypass the state machine), and explicit Seller Admin/Warehouse Worker regression tests. `npm run lint`, `npm run typecheck`, `npm run build`, and `prisma validate`/`prisma generate` are all clean as of `aaff752`.

**Browser verification**: see §7 - all four roles, full live lifecycle (assign → confirm → advance → reassign → deliver), a different driver's direct-URL 404, reassignment immediately revoking the previous driver's visibility, the assign control correctly hidden on a terminal order, Warehouse Worker's dashboard/inbox unaffected, and a responsive check at 375px/768px.

## 22. Observability: privacy-conscious Sentry error/exception reporting

Commit `a13a86f`. Picked up the "error tracking/observability wired up in production" item that had sat in this file's proposed-next-phase list since Phase 1E (§14's structured logger was always the deliberately vendor-free local groundwork for this). Scope was approved across several review rounds before any code was written (vendor/region choice → env-var/client-vs-server separation → exact DSN validation rule → final sign-off), the same "propose, review, approve" discipline every phase since 1F-B1 has followed. **No schema, migration, RLS, auth, or capability change of any kind** - this is a pure application-layer/config addition: one new dependency, a handful of new files under `src/instrumentation*.ts`/`src/lib/observability/`, and two one-line call sites in existing files.

**Vendor and region.** Sentry, `@sentry/nextjs@10.75.2` (exact pin, not a caret range - confirmed compatible with this repo's `next@16.3.5` via its own `peerDependencies`). **DE-region DSN enforcement, no silent US fallback**: `isValidDeRegionDsn` (`src/lib/observability/sentry-config.ts`) requires both `URL.protocol === "https:"` and `URL.hostname` (not `.host`, so an explicit port can't defeat the check) ending in `.ingest.de.sentry.io` - a DSN that's merely HTTP, malformed, missing, or pointed at any non-DE-region host (including a look-alike host that only contains the suffix mid-string) is treated as fully disabled rather than sent anywhere. This is a code-level guarantee, not a dashboard setting someone could get wrong later without it being caught.

**Independently gated server/client enablement - six env vars, two fully separate pairs**, none inferred from `NODE_ENV`:

| | Server (Node runtime only) | Client (browser bundle) |
|---|---|---|
| Enable flag | `SENTRY_ENABLED` | `NEXT_PUBLIC_SENTRY_ENABLED` |
| DSN | `SENTRY_DSN` | `NEXT_PUBLIC_SENTRY_DSN` |
| Environment tag | `SENTRY_ENVIRONMENT` | `NEXT_PUBLIC_SENTRY_ENVIRONMENT` |

Server reporting requires `SENTRY_ENABLED === "true"` **and** a DE-region-valid `SENTRY_DSN`; client reporting requires the same on its own `NEXT_PUBLIC_` pair. Neither side can be turned on by the other's vars - proven directly by test (§5's observability entry, "does not initialize when only the server-side pair is set"). Both default to disabled, including under a local `next build && next start` (this project's own documented workaround for `next dev`'s single-instance lock, per §7's environment notes) - deliberately *not* gated on `NODE_ENV==="production"`, specifically because that workaround runs in production mode on a dev machine.

**Privacy/minimization - what is never sent, regardless of SDK defaults:**
- `sendDefaultPii: false` explicit on both `Sentry.init` calls.
- No Session Replay integration, no performance tracing/APM (`tracesSampleRate: 0`, `replaysSessionSampleRate: 0`, `replaysOnErrorSampleRate: 0` on the client).
- No request headers (not even `User-Agent`), no request/response bodies, no cookies, no authorization/session tokens - `sentryBeforeSend` (`src/lib/observability/sentry-scrub.ts`) deletes `event.request.headers`/`.cookies`/`.data` unconditionally rather than allowlisting individual header names.
- No Sentry user identity (`event.user` deleted; `Sentry.setUser()` is never called anywhere in this codebase) and no tenant identifier (`tags.tenantId` stripped defensively, even though nothing sets one today - a deliberate backstop against a future call site adding one without updating this file).
- URL query strings stripped from `request.url`/`request.query_string` (`stripQueryString`).
- Email- and phone-shaped substrings redacted from `event.message` and exception values via regex (`redact`).
- **Known server-secret literals stripped from outbound server events** - regex-shape redaction alone can't catch an opaque secret like `AUTH_SECRET`, which has no distinguishing shape. `createSentryBeforeSend(knownSecrets)` (same file) takes an explicit allowlist of literal values to strip; only `src/instrumentation.ts` (server-only, never bundled to the browser) ever calls it with the real `DATABASE_URL`/`MIGRATE_DATABASE_URL`/`AUTH_SECRET` values read from `process.env` - the shared scrub module itself stays pure, with zero `process.env` reads and zero server-only imports, specifically so it's safe for `instrumentation-client.ts` to import too. The client's `beforeSend` uses the plain regex-only variant (`sentryBeforeSend`, no secrets list), since the browser bundle never has these values to begin with.
- All SDK-auto breadcrumbs dropped in this first phase (`sentryBeforeBreadcrumb` always returns `null`; `event.breadcrumbs` is also emptied in `beforeSend` as a second backstop) - not something a future phase couldn't reconsider, just not needed yet and one less scrubbing surface to maintain now.
- The existing structured logger (`src/lib/logging/logger.ts`, §14) is **completely unchanged** - no `logger.error` call is forwarded to Sentry as a breadcrumb or event. Reason, per the approved scope: logger metadata is intentionally generic/arbitrary today, so forwarding it wholesale would open a larger accidental PII/business-data egress surface than the capture paths below actually need.

**Capture paths - explicit and narrow, not "capture everything":**
- Server request/render/action errors: `src/instrumentation.ts`'s `register()`/`onRequestError`, the stable Next.js 16 hook (confirmed against `node_modules/next/dist/docs/.../instrumentation.md` per this repo's `AGENTS.md` convention - and where the vendored docs and the actual shipped type disagreed, on `RequestErrorContext`'s `renderType` field, the real `.d.ts` was what got followed, not the docs page).
